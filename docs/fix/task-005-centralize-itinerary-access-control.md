# Task 005: しおり認可とセッションキー生成を共通化する

- 観点: コードの冗長性、セキュリティ
- 優先度: Medium

## 問題

各Viewが、しおり取得、閲覧認証、編集認証、パスワード画面、JSON 403を個別実装しています。既にTask 001のような認可漏れが生じており、`edit_auth_{pk}` と `view_auth_{pk}_{token}` の形式も散在しています。

## 実装指示

1. 閲覧用・編集用のアクセス判定を共通のMixin/decorator/helperへ集約する。
2. HTMLリクエストは適切なパスワード画面へ、JSON APIは401/403へ返す方針を共通化する。
3. セッションキー生成を関数化し、可能ならtokenまたは認可世代を含め、パスワード再設定後に既存編集セッションを無効化できる設計にする。
4. `self.itinerary` をdispatchで一度だけ取得し、context/postでの再取得を除く。
5. V1/V2で必要な挙動差を明示し、共通化によってV1の仕様を暗黙に変更しない。

## テスト

- 全V2閲覧URL・編集URL・更新APIについて、パスワードなし／閲覧のみ／編集済みの権限表をパラメータ化テストする。
- パスワード再設定後、旧編集セッションで変更できない。
- HTMLとJSONで期待する応答種別・ステータスになる。
