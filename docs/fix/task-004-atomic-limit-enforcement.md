# Task 004: 件数上限とAI日次上限を競合に対して原子的にする

- 観点: セキュリティ、処理速度、データ整合性
- 優先度: High

## 問題

行きたい場所、1日当たり予定数、AIコンシェルジュ日次回数は「countしてからcreate」の別処理です。同時リクエストでは両方が上限未満と判定し、上限を超えて保存または外部APIを実行できます。AIでは課金を伴う呼び出し前の予約もありません。

対象例: `can_add_want_to_go`、`count_schedules_for_day`、`ConciergeV2View._get_today_usage_count` と各作成処理。

## 実装指示

1. PostgreSQL本番環境で有効な原子化方式を採用する。親 `Itinerary` の `select_for_update()`、利用枠テーブル、原子的カウンタのいずれかを設計する。
2. AI利用枠は外部API呼び出し前に予約し、失敗時に戻すか、失敗も消費するかを仕様化する。長い外部通信中にDBロックを保持しない。
3. 行きたい場所・予定の作成と上限確認を同一トランザクションで行う。
4. 現在のJSONエラー形式と上限メッセージを維持する。

## テスト

- `TransactionTestCase` 等で同時リクエストを模擬し、上限を超えない。
- AI APIモックの呼び出し回数も日次上限を超えない。
- API失敗時の利用枠の扱いが仕様どおりになる。
